# Technical notes

How the Windows cursors are built, and the reasoning behind each choice.

## How Windows sizes cursors

The system cursor size comes from two settings:

1. **Display scale, in steps.** At the default pointer size, the nominal size is 32 px below 150%, 48 px at 150–199%, 64 px at 200–299%, 96 px at 300–399%, and 128 px at 400% and above ([Microsoft: Cursor Sizes](https://learn.microsoft.com/en-us/windows/win32/menurc/about-cursors#cursor-sizes)). For example, 125% still uses 32 px.
2. **Pointer size slider** (Settings › Accessibility › Mouse pointer and touch). Positions 1–15 set `HKCU\Control Panel\Cursors\CursorBaseSize` to 32, 48, 64 … 256, which multiplies the nominal size by 1, 1.5, 2 … 8.

When Windows loads a `.cur` or `.ani`, it looks for an image of exactly the size it wants. If there isn't one, it takes the nearest image, preferring a larger one, and resamples it. Resampling is what makes cursors blurry.

We confirmed this on Windows 11 (build 26200) with a test cursor whose images are each a different solid color. `LoadImage` returned the exact-size image when one existed. Otherwise it chose the next larger image, and it applied the pointer-size multiplier itself.

### The original bug

Version 1.0 was generated by the upstream Linux pipeline, which renders the 24-unit SVGs at 24 × {1, 1.25, 1.5, 2, 2.5, 3, 4} = **24, 30, 36, 48, 60, 72, 96 px**. Windows asks for 32 × step × pointer size. These sets only overlap in a few places (48, 96 and, at larger pointer sizes, 72). So the cursors were exact in some configurations and resampled in all the others, including the default 100%, 32 px case.

## Size ladders

| File type | Embedded sizes (px) | Exact for |
| --- | --- | --- |
| Static `.cur` | 32, 48, 64, 72, 96, 128, 144, 192, 256 | Pointer sizes 1–3 at every display scale |
| Animated `.ani` | 32, 48, 64, 96, 128, 192, 256 | Pointer sizes 1 and 3 at every display scale |

256 px is the largest size the ICO/CUR directory can describe, and also the largest pointer size.

### Why animated cursors carry fewer sizes

On Windows 11, `LoadImage` silently returns `NULL` (with `GetLastError() == 0`) for an `.ani` whose frames contain too much image data. With the full 15-size ladder we first tried, frames of about 80 KB failed while frames up to about 79 KB loaded. With four images per frame, failures started around 91 KB, and a single-image frame still loaded at 124 KB. So the budget depends on the image count as well as the byte size. Static `.cur` files show no such limit. The rule isn't documented and may differ between Windows builds; we found only anecdotal reports ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2515079/animated-cursor-file-size-limit)).

To stay safe, `build.py`:

- keeps animated frames to 7 sizes (worst case about 50 KB per frame),
- fails the build if any frame exceeds `ANI_FRAME_BUDGET` (56 KiB), and
- on Windows, loads every generated file with `LoadImageW` at every ladder size and fails if any load returns `NULL`.

### Performance

Windows decodes only the image it displays, so extra sizes don't slow anything down. Measured with `LoadImageW` on Windows 11:

| File | Load time |
| --- | --- |
| Static `.cur`, 1 size vs 9 sizes | ~1 ms either way |
| Animated `.ani`, 24 frames, 7 sizes | ~8 ms (1.0's files: 7–31 ms) |

## Rendering

- **Source:** SVGs from [keeferrourke/capitaine-cursors](https://github.com/keeferrourke/capitaine-cursors) at commit `06c8843`, vendored in `src/svg/{dark,light}`. Only the files used on Windows are included.
- **Renderer:** [resvg](https://github.com/linebender/resvg) via `resvg-py`. Each size is rendered directly from the vectors, so there's no bitmap resampling. The output is visually identical to upstream's Inkscape renders.
- **Format:** each image is a 32-bit RGBA PNG inside the `.cur` directory (supported since Windows Vista), optimized with Pillow.
- **Hotspots:** defined on the 24-unit grid and mapped to `floor(coord × size / 24)`, the pixel that contains the point. The pen hotspot is set to the pencil tip (3.64, 20.68). Upstream uses (4, 4), which is empty space about 14 px from the tip at 24 px.
- **Animation:** `working.ani` and `wait.ani` have 24 frames each at 2 jiffies (33 ms, about 30 fps, one turn every 0.8 s), close to upstream's 30 ms. Each frame is a complete multi-size `.cur`, flagged `AF_ICON`, with `INAM`/`IART` credits in a RIFF `INFO` list.

## Installer

`build.py` generates both `install.inf` files from one template, so they can't drift apart:

- `[DefaultInstall]` copies the files to `%WINDIR%\Cursors\Capitaine Cursors (<Variant>)` and adds a system-wide scheme under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Control Panel\Cursors\Schemes`. Both steps need administrator rights.
- `[DefaultUninstall]` deletes the files and the scheme value. Run it with `rundll32.exe setupapi.dll,InstallHinfSection DefaultUninstall 132 <path>`.
- The installer doesn't switch the active scheme. The user picks it in `main.cpl`, which applies it immediately and doesn't depend on which account approved the elevation prompt.

`.gitattributes` keeps the INF files as CRLF in every checkout. The release zip is written with fixed timestamps, so rebuilding from the same sources produces the same archive.
