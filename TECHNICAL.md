# Technical notes

How the Windows cursors are built, and the reasoning behind each choice.

## Build (since 3.0)

3.0 is built by [w11-cursor-toolkit](https://github.com/hervad/w11-cursor-toolkit), the same toolchain as the other
`*-w11-hidpi` cursor themes, instead of this repo's own `build.py`. Everything theme-specific is in
[`theme.toml`](theme.toml): roles, hotspots, sizes, variants and their colours. The SVGs come from upstream through the `upstream/`
submodule (commit `06c8843`, upstream's latest); 2.0 vendored the same 122 files, byte-identical.

**Equivalence with 2.0:** every cursor, every animation frame and every size present in both builds was compared for
both variants - 906 images, **0 hotspot differences and 0 pixel differences**.

## How Windows sizes cursors

Windows picks the image size as `CursorBaseSize × factor`, where `CursorBaseSize` is the pointer-size slider
(32, 48, 64 … 256) and the factor depends on the display scale: **1.0 from 100 % to 149 %, 1.5 from 150 % to 199 %**
(measured on Windows 11 25H2; see the toolkit's
[SIZE_POLICY.md](https://github.com/hervad/w11-cursor-toolkit/blob/main/docs/SIZE_POLICY.md)). Higher scales are
assumed to continue the pattern (2.0, 2.5, 3.0). If the file has that exact size, Windows uses it; otherwise it
resamples the closest one. 2.0's table (×2 at 200 %, ×3 at 300 %, ×4 at 400 %, after Microsoft's documentation) was
not measured.

### The original bug (1.0)

1.0 was generated by the upstream Linux pipeline, which renders the 24-unit SVGs at 24 × {1, 1.25, 1.5, 2, 2.5, 3, 4}
= 24, 30, 36, 48, 60, 72, 96 px. Windows asks for other sizes, so the cursors were resampled in most configurations,
including the default 100 %, 32 px case.

## Size ladders

| File type | Embedded sizes (px) |
| --- | --- |
| Static `.cur` | 32, 48, 64, 72, 80, 96, 112, 120, 128, 144, 160, 168, 176, 192, 200, 208, 216, 224, 240, 256 |
| Animated `.ani` | 32, 48, 64, 72, 80, 96, 120, 128, 144, 192, 256 |

Every 2.0 size is still there (static 32–256 in 9 steps, animated 32, 48, 64, 96, 128, 192, 256); 3.0 adds the sizes the
measured rule asks for, such as 80 px at pointer size 4 and 72/120/144 px at 150 %.

### Animation limit (measured)

Windows refuses an `.ani` frame in which an image starts past byte 65,535 of the frame; the total file size doesn't
matter (a 29 MB test file loads). Dark and Light's largest image start is 57,822 bytes, so all 11 animated sizes fit.
The files are larger than before (`busy.ani` about 1.6 MB). 2.0's explanation (frames of "about 80 KB" failing)
described the same limit before it was measured.

The colour variants compress less well, because their spinners have more colour detail. The largest image start is
63,808 bytes (Palenight Light, 97 % of the limit); `validate` warns above 90 % and fails above the limit, and every file
of every variant loads with the real Windows loader. The largest file is 1.81 MB (Palenight Dark `busy.ani`), so 3.2
raises the download cap (`ani_budget_bytes`) from 1.8 to 1.85 MB. That cap only keeps downloads small; it is not a
Windows limit.

## Rendering

- **Source:** SVGs from [keeferrourke/capitaine-cursors](https://github.com/keeferrourke/capitaine-cursors) at commit
  `06c8843`, via the `upstream/` submodule (`src/svg/dark`, `src/svg/light`).
- **Renderer:** [resvg](https://github.com/linebender/resvg), as in 2.0. Each size is rendered directly from the
  vectors, so there's no bitmap resampling.
- **Format:** each image is a 32-bit RGBA PNG inside the `.cur` directory.
- **Hotspots:** defined on the 24-unit grid and mapped to `floor(coord × size / 24)`, the pixel that contains the
  point (`hotspot_mode = "pixel"`). The pen hotspot is on the pencil tip (3.64, 20.68); upstream uses (4, 4), which is
  empty space about 14 px from the tip at 24 px.
- **Animation:** busy and working have 24 frames each at 2 jiffies (33 ms, about 30 fps, one turn every 0.8 s), close to
  upstream's 30 ms.

## Colour variants (since 3.2)

The 16 colour variants use the Dark or Light SVGs unchanged and replace colours as text in the SVG source before
rendering (`recolor` in [`theme.toml`](theme.toml), applied top to bottom). The shapes, sizes, hotspots and
animation are the same as Dark and Light, and Dark and Light themselves are byte-identical to 3.1.

Capitaine uses a fixed set of colours, so each one has a role: `#1a1a1a` is the Dark body, `#fefefe` the Light body,
`fill="#fff"` the Dark outline, `#3daee9` the help badge and resize dots, `#f67400` the move dot, `#ed1515` the
unavailable sign, and six colour pairs plus a grey make the spinner. Two details need more than a colour swap:

- **Shapes without a colour.** Light's outline and a few Dark bodies (pencil, up-arrow) have no `fill` attribute, so
  SVG draws them black and a text replacement can't find them. The variants add a `fill` to the root `<svg>`, which
  those shapes inherit.
- **Shadows stay black.** The soft shadows also have no `fill`. A tinted shadow made `busy.ani` about 50 % larger
  (blurred colour compresses badly), so the shadows get an explicit black fill.

**Nord, Gruvbox, Palenight** reproduce [sainnhe's fork](https://github.com/sainnhe/capitaine-cursors) as in its
release r5 (2022-06-06): its `patch.sh` colour maps, including the outline colour. Later commits on its master
(darker shadows, keeping the white outline) were never released, so they aren't followed.

**Catppuccin Mocha, Dracula, Rosé Pine, Tokyo Night, Solarized** colour the whole pointer with one signature colour
of the palette, with the palette's dark base as the outline and its colours on the spinner and accents. A first draft
used each palette's background colour for the pointer, as most palette ports do, but these backgrounds are all nearly
black: measured with CIEDE2000 on the built files, two of them differed by ΔE 2.5, which is not visible at cursor size.
The signature colours are chosen so that no two are closer than ΔE 15 (Dracula uses pink because its purple matches
Catppuccin's mauve). The darker shade of each spinner colour is derived as HSL lightness −9 %, saturation +5 %.

**Blue, Red, Green, Amber, Purple** are Material Design colours with a dark outline and the original spinner. Each
pointer colour has at least 3:1 contrast with its outline (WCAG's minimum for graphics).

**Dark's white parts and the dots (fixed in 3.2.1).** Besides each pointer's outline, Dark's artwork has white
*parts* in four cursors: the Unavailable disc, the Busy spinner's rim, the Working spinner's rim, and the Help badge's
ring and "?". 3.2.0 turned the white outline dark for the ten palette and colour variants, and that rule darkened
these parts too (a dark Unavailable disc, dark spinner rims and Help rings); in Tokyo Night and Blue the resize dots
and the Help badge also had the pointer's own colour. Since 3.2.1 only the pointer outline turns dark:
- the **spinner rims and the Help ring stay light** (the palette's light text colour, white for Blue/Red/Green/Amber/
  Purple, whose Busy is therefore Capitaine Dark's own). The Help "?" is white for those five, as in Dark; the five
  palettes keep a dark "?", because a light one is unreadable on their pastel badges (1.3-1.5:1);
- the **Unavailable disc stays light** (a rule anchored on that circle only): the palette's light text colour, white
  for Blue/Red/Green/Amber/Purple. Their Unavailable is therefore Capitaine Dark's own, the same in all five. Where the
  palette's red was too pale on the light disc, the sign uses the same palette's darker red (Catppuccin Latte, Dracula
  Alucard, Rosé Pine Dawn, Tokyo Night `#914c54`): every sign has at least 3:1 contrast with its disc;
- **dots and badges differ from the pointer:** Tokyo Night uses its cyan `blue1`, Blue's Help badge is orange, and
  Blue/Red/Green/Amber/Purple have white resize and Move dots. Every dot is at least CIEDE2000 15 from its pointer.

Nord, Gruvbox and Palenight keep sainnhe's colours, including their softer signs (2.6-3.4:1).

**Checked on every build.** `theme.toml` lists nine `[[checks]]` (toolkit v0.6.0) that sample the built cursors at
fixed points and fail `validate` if a colour rule is broken: the pointer body against its outline (contrast ≥ 3:1),
the Unavailable disc (light) and its sign (≥ 3:1), the Busy and Working rims and the Help ring (light, except in the
Light artwork, where they are black by design), and the resize dot, Move dot and Help badge (CIEDE2000 ≥ 15 from the
pointer). Run against the 3.2.0 files they report exactly the problems fixed in 3.2.1.

## Installer

The toolkit writes `install.inf` and `uninstall.cmd`. **Install** copies the files to
`%WINDIR%\Cursors\Capitaine <Variant> W11 HiDPI` (since 3.1; 2.0-3.0 used *Capitaine Cursors (<Variant>)*), registers the
scheme for the current user
under `HKCU\Control Panel\Cursors\Schemes`, applies it and opens Mouse Properties. **Uninstall** removes the scheme entry
and opens Mouse Properties; the folder is deleted by hand. 2.0 registered its schemes for all users under `HKLM` and
didn't apply them; INSTALL.md shows how to remove those before upgrading.

**Zips (since 3.2):** each Dark + Light pair (Capitaine, Nord, Gruvbox, Palenight) ships as one zip with a folder per
scheme, each with its own `install.inf` and `uninstall.cmd` (`package` in [`theme.toml`](theme.toml), toolkit v0.5.0);
the other ten schemes have a zip each, so 14 zips in total. A pair is still two schemes in Mouse Properties, because
a Windows scheme is exactly one set of cursors. Dark and Light keep their 3.1 scheme names and folders, so upgrading
from 3.1 leaves no old schemes behind to clean up.
