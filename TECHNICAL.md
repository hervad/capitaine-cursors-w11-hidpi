# Technical notes

How the Windows cursors are built, and the reasoning behind each choice.

## Build (since 3.0)

3.0 is built by [w11-cursor-toolkit](https://github.com/hervad/w11-cursor-toolkit), the same toolchain as the other
`*-w11-hidpi` cursor themes, instead of this repo's own `build.py`. Everything theme-specific is in
[`theme.toml`](theme.toml): roles, hotspots, sizes, variants. The SVGs come from upstream through the `upstream/`
submodule (commit `06c8843`, upstream's latest); 2.0 vendored the same 122 files, byte-identical.

**Equivalence with 2.0:** every cursor, every animation frame and every size present in both builds was compared for
both variants - 906 images, **0 hotspot differences and 0 pixel differences**.

## How Windows sizes cursors

Windows picks the image size as `CursorBaseSize × factor`, where `CursorBaseSize` is the pointer-size slider
(32, 48, 64 … 256) and the factor depends on the display scale: **1.0 from 100 % to 149 %, 1.5 from 150 % to 199 %**
(measured on Windows 11 25H2; see the toolkit's
[SIZE_POLICY.md](https://github.com/hervad/w11-cursor-toolkit/blob/main/docs/SIZE_POLICY.md)). Higher scales are
assumed to continue the pattern (2.0, 2.5, 3.0). If the file has that exact size, Windows uses it; otherwise it
resamples the closest one. 2.0's table (×2 at 200 %, ×3 at 300 %, ×4 at 400 %, after Microsoft's documentation) was
not measured.

### The original bug (1.0)

1.0 was generated by the upstream Linux pipeline, which renders the 24-unit SVGs at 24 × {1, 1.25, 1.5, 2, 2.5, 3, 4}
= 24, 30, 36, 48, 60, 72, 96 px. Windows asks for other sizes, so the cursors were resampled in most configurations,
including the default 100 %, 32 px case.

## Size ladders

| File type | Embedded sizes (px) |
| --- | --- |
| Static `.cur` | 32, 48, 64, 72, 80, 96, 112, 120, 128, 144, 160, 168, 176, 192, 200, 208, 216, 224, 240, 256 |
| Animated `.ani` | 32, 48, 64, 72, 80, 96, 120, 128, 144, 192, 256 |

Every 2.0 size is still there (static 32–256 in 9 steps, animated 32, 48, 64, 96, 128, 192, 256); 3.0 adds the sizes the
measured rule asks for, such as 80 px at pointer size 4 and 72/120/144 px at 150 %.

### Animation limit (measured)

Windows refuses an `.ani` frame in which an image starts past byte 65,535 of the frame; the total file size doesn't
matter (a 29 MB test file loads). Capitaine's largest image start is 57,822 bytes, so all 11 animated sizes fit. The
files are larger than before (`busy.ani` about 1.6 MB). 2.0's explanation (frames of "about 80 KB" failing) described
the same limit before it was measured.

## Rendering

- **Source:** SVGs from [keeferrourke/capitaine-cursors](https://github.com/keeferrourke/capitaine-cursors) at commit
  `06c8843`, via the `upstream/` submodule (`src/svg/dark`, `src/svg/light`).
- **Renderer:** [resvg](https://github.com/linebender/resvg), as in 2.0. Each size is rendered directly from the
  vectors, so there's no bitmap resampling.
- **Format:** each image is a 32-bit RGBA PNG inside the `.cur` directory.
- **Hotspots:** defined on the 24-unit grid and mapped to `floor(coord × size / 24)`, the pixel that contains the
  point (`hotspot_mode = "pixel"`). The pen hotspot is on the pencil tip (3.64, 20.68); upstream uses (4, 4), which is
  empty space about 14 px from the tip at 24 px.
- **Animation:** busy and working have 24 frames each at 2 jiffies (33 ms, about 30 fps, one turn every 0.8 s), close to
  upstream's 30 ms.

## Installer

The toolkit writes `install.inf` and `uninstall.cmd`. **Install** copies the files to
`%WINDIR%\Cursors\Capitaine Cursors (<Variant>)` (the same folder as 2.0), registers the scheme for the current user
under `HKCU\Control Panel\Cursors\Schemes`, applies it and opens Mouse Properties. **Uninstall** removes the scheme entry
and opens Mouse Properties; the folder is deleted by hand. 2.0 registered its schemes for all users under `HKLM` and
didn't apply them; INSTALL.md shows how to remove those before upgrading.
